# 5. Requerimientos No Funcionales

Como complemento indispensable a los requerimientos funcionales, se definen los siguientes **8 Requerimientos No Funcionales (RNF)** que establecen los estándares de calidad técnica, seguridad, arquitectura y desempeño para el sistema **MaxiConecta Marketplace y Ventas**.

---

## Matriz de Requerimientos No Funcionales

| ID | Atributo de Calidad | Descripción del Requerimiento | Criterio de Aceptación / Mecanismo Técnico |
| :--- | :--- | :--- | :--- |
| **RNF-01** | **Seguridad** | Proteger contraseñas, tokens de sesión y rutas privadas mediante cifrado de extremo a extremo, JWT firmados y control de acceso basado en roles (RBAC). | - Uso de Supabase Auth para hashing seguro de credenciales (bcrypt/argon2).<br/>- Validación de tokens JWT en el API Gateway para todas las rutas privadas.<br/>- Separación de privilegios entre Clientes, Cajeros, Gerentes y Administradores. |
| **RNF-02** | **Rendimiento** | Responder a las consultas y operaciones habituales (búsqueda facetada, gestión de carrito, procesamiento de checkout) en tiempos sub-segundo incluso bajo concurrencia. | - Tiempos de respuesta para consultas de catálogo < 300 ms.<br/>- Uso de Redis como caché en memoria para carritos activos y bloqueo temporal de stock.<br/>- Consultas optimizadas con índices en PostgreSQL para búsquedas de productos. |
| **RNF-03** | **Disponibilidad** | Garantizar la operación continua del servicio de marketplace y ventas en entorno de producción, minimizando tiempos de inactividad programados y no programados. | - Arquitectura desacoplada basada en contenedores Docker.<br/>- Si un microservicio auxiliar experimenta fallas temporales, no debe bloquear la navegación general del catálogo. |
| **RNF-04** | **Escalabilidad** | Facilitar la incorporación de nuevos módulos funcionales, canales de venta (aplicaciones móviles, kioscos) o vendedores externos sin necesidad de rediseñar la arquitectura base. | - Arquitectura de microservicios con comunicación desacoplada y sin estado (*stateless*).<br/>- API Gateway centralizado para enrutar nuevos endpoints y servicios. |
| **RNF-05** | **Mantenibilidad** | Separar responsabilidades estrictas entre microservicios para que el código sea modular, fácil de corregir, extender, probar y desplegar independientemente. | - Backend en FastAPI estructurado en capas limpias (routers, schemas, services, repositories).<br/>- Frontend en Vue 3 modularizado por dominios (Marketplace, POS, Admin) con Pinia stores y componentes reutilizables. |
| **RNF-06** | **Usabilidad** | Ofrecer una interfaz clara, intuitiva y accesible tanto para el cliente final en compras digitales, como para el cajero en sucursal y el personal administrativo. | - Diseño con Tailwind CSS y componentes Flowbite con diseño responsive (móvil y escritorio).<br/>- Flujo POS optimizado para lectura de código de barras y cobro en menos de 3 clics/interacciones.<br/>- Checkout guiado paso a paso con validaciones visuales en tiempo real. |
| **RNF-07** | **Interoperabilidad** | Exponer y consumir contratos de API REST claros, versionados y exhaustivamente documentados para facilitar la integración con los demás sistemas del ERP. | - Documentación interactiva OpenAPI (Swagger UI) y esquemas JSON estandarizados en cada microservicio.<br/>- Respeto riguroso de los contratos de interoperabilidad (códigos RIO-INV, RIO-PAG, RIO-CON, RIO-CRM, RIO-ENT, RIO-PRD). |
| **RNF-08** | **Trazabilidad** | Registrar de forma inmutable y auditable los eventos y cambios de estado relevantes de cada orden, transacción de pago y movimiento de inventario. | - Tabla de auditoría en PostgreSQL registrando usuario, timestamp, IP, entidad y payload antes/después.<br/>- Registro estructurado de logs en formato JSON para diagnósticos operacionales. |
